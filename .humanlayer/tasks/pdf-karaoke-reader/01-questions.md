# Phase 1 — Questions

Task: a local-only PDF reader that reads a dropped PDF aloud with Kokoro TTS and
highlights each word as it is spoken (karaoke e-reader).

The goal directive says not to block on the user, so each open question below is
recorded with the decision taken and the reasoning. Anything marked **REVISIT**
is a place where a different answer would change the design materially.

## Q1. Where does word-level timing come from?

Kokoro has no word-timestamp API. `fastkokoro` exposes OpenAI's
`/v1/audio/speech`, which returns audio bytes and nothing else.

**Decision:** synthesise **one sentence per request**, measure that sentence's
exact audio duration, then distribute the duration across the sentence's words
by an estimated speech cost (vowel groups + character length + punctuation
pause weight).

Sentence boundaries are therefore *exact*; word boundaries inside a sentence are
*estimated*. For a karaoke reader this is the right trade: drift never
accumulates past a sentence, and the estimate is a pure function — which makes
it the single best property-testing target in the codebase.

**REVISIT** if word-accurate alignment is needed: run forced alignment over the
generated audio, or switch to the PyTorch `kokoro` package whose `KPipeline`
exposes per-token `start_ts`/`end_ts`. Both add heavy dependencies (`kokoro`
pins `python<3.13` and needs a system `espeak-ng`), so neither is justified yet.

## Q2. `fast-kokoro` or `fastkokoro`?

There is no `fast-kokoro` on PyPI. There is `fastkokoro` 0.7.0. Confirmed it
serves the `am_adam` voice requested.

**Decision:** `fastkokoro[cpu]` run as a sidecar server on `:8880`. The FastAPI
app talks to it over HTTP behind a `SpeechSynthesizer` protocol, so tests
substitute a deterministic fake and never need the model.

## Q3. Does the browser or the server own playback position?

**Decision:** the browser. The API returns `(audio, timeline)` once; the
`<audio>` element's `currentTime` drives highlighting client-side. No websockets,
no server-side playhead. This keeps the API pure request/response and makes the
highlight logic a pure function of `(timeline, t)` — property-testable in
TypeScript with Hegel exactly as it is in Python with Hypothesis.

## Q4. How much PDF do we read?

**Decision:** one page at a time. Synthesising a 300-page book on first upload
is not "very simple". Page N is synthesised on demand and cached.

## Q5. What makes the docs assert that the UI still works?

**Decision:** every screenshot and GIF in the Diataxis site is written by a UI
test, never by hand. A doc image that cannot be regenerated by a passing test is
a bug. Scenarios tagged `@docs` emit artefacts; scenarios tagged `@property` do
not (100 shrunk random cases make terrible documentation).

## Q6. Python version?

`kokoro-onnx` pins `<3.14`; system Python is 3.14.6. **Decision:** `uv` pins the
API to 3.12, which satisfies every candidate TTS package.

## Q7. Node version?

pnpm 11 needs Node >= 22.13; the nvm default on this machine is 22.10.
Node 26.7.0 is present at `/opt/homebrew/opt/node/bin`. **Decision:** pin it via
`.nvmrc` + an explicit `PATH` prefix in the Makefile so the toolchain is not
dependent on the developer's shell.
